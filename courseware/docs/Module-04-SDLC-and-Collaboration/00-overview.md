# Module IV: Software Development Lifecycle & Collaboration

## Module Overview

Welcome to Module IV, where we shift our focus from individual programming to the broader context of how professional software teams work together. In the previous modules, you established what modern programming actually is, built the working habits that make it sustainable, and set up the development environment—the operating system, the command line, and VS Code—that you'll be working in from here on.

Now we explore the **Software Development Lifecycle (SDLC)** — the structured process by which software teams plan, build, test, and deploy applications. You'll discover why certain practices, tools, and workflows have become standard across the industry, and you'll gain practical experience with the collaboration tools that every modern programmer uses daily.

This module is specifically designed for career changers. You likely have experience from other fields — perhaps product management, manufacturing, finance, or operations. We'll draw explicit comparisons between software development and processes you may already know, helping you recognize familiar patterns in new contexts.

> **🔗 Course Project Thread: CivicTrack**
> Here you treat [CivicTrack](../../course-project/README.md)—our running citizen service-request example—as a team artifact, not a solo project. You'll put its README under version control, branch to make a change, and review that change through a pull request, just as a real CivicTrack team would. The Git and Markdown skills in this module are exactly how that team keeps its docs and code in sync.

## Learning Objectives

By completing Module IV, you will be able to:

1. **Understand the Software Development Lifecycle** — Explain the major phases of software development and why each phase matters
2. **Distinguish between development methodologies** — Compare Waterfall, Agile/Scrum, Kanban, Lean, and DevOps approaches, and understand when each is appropriate
3. **Work with version control in Git** — Use Git to manage code locally, create branches, and prepare work for team collaboration
4. **Collaborate through code review workflows** — Understand pull requests and how teams maintain code quality through peer review
5. **Communicate technically in writing** — Write clear documentation in Markdown that explains code and decisions to other programmers
6. **Recognize quality and technical debt** — Identify what makes code "good," understand the concept of technical debt, and appreciate why teams invest in code quality
7. **Understand team dynamics and roles** — Explain the different roles in a software team and how they contribute to successful projects

## Key Themes Throughout This Module

### **From Individual to Team**
You've spent three modules thinking like an individual programmer solving problems. Now you're learning to think like a team member coordinating with others on shared goals.

### **Visible Structure, Hidden Complexity**
The software processes you'll learn (sprints, code reviews, branching strategies) create structure that makes teamwork possible. This structure can feel like bureaucracy until you've worked on a team without it.

### **Tools Enable Practices**
Git, pull requests, and automated testing are not just features — they're tools that make specific teamwork practices possible. Understand the problems they solve, and the tools become logical rather than arbitrary.

### **Quality is Built In, Not Added On**
Many software teams treat quality (testing, code review, documentation) as something added at the end. Modern practices embed quality throughout the process.

## A Note on Methodologies

You'll notice this module covers many different approaches to software development: Waterfall, various Agile flavors, Lean, DevOps. You may wonder, "Which one is right?"

The honest answer: it depends on context. Different teams, projects, and organizations need different approaches. What matters is understanding the principles behind each approach and being able to adapt when you join a team. We'll help you develop that flexibility.
